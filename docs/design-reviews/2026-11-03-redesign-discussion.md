## 2. 第一轮：独立方案

Claude Code 的主要主张：

> “原生 CLI 负责干活，可以拿到更多自由。宿主只掌握四件事：有效状态、责任与授权、证据与验收、副作用提交。”

它提出在现有 Run 之上增加 Goal、PlanVersion、StateEntry、Effect 和 ContextManifest，倾向 Goal 绑定 Thread、同 Goal 串行。执行分只读、隔离工位、本机委托；默认 fresh，只在同一责任链续接 session。它主张平台数据库为状态真相源，原始来源和派生摘要分开，合入与部署分别核实。

它对初稿最有价值的挑战：

1. **Git 元数据风险。** linked worktree 共享 common dir；若 Agent 可改 hooks/config/refs，就可能影响主仓和后续宿主操作。
2. **候选修改验证政策。** 不能让候选代码自行删掉必需检查，或改 AGENTS 后宣称旧约束不再适用。
3. **MCP 与 loopback。** 项目子进程可能拿到同一工具凭据；放开 loopback 可能暴露本机管理服务。
4. **输入与事务。** inbox 纳入、manifest 与 Attempt 必须协调，避免补充消息丢失或错报送达。
5. **恢复策略版本。** 已中断 Run 不能恢复时突然切换上下文政策，破坏冻结输入与防空转保护。

这些问题已进入主稿的执行目录、权限、输入回执和迁移设计。

## 3. 第二轮：Codex 反驳与 Claude Code 回应

### 3.1 长期目标是否绑定单个 Thread

Codex 认为 Goal 绑定 Thread 且只能串行会延续原来的结构限制，选择 Workspace 下持久 Task，可关联多个 Thread/Run，独立子任务并行。

Claude Code 条件同意，承认其原方案会卡住长工程，并提出子任务不应挤满 UI、写任务必须隔离、并行写入应限制资源。

**最终选择：** Task 跨 Thread；同 Task 单活跃 Run，独立子 Task 可并行。默认最多四个并行分支，其中两个 writer；子任务在根任务下折叠，提问统一到“需要你处理”。参数是待真实任务校准的初始政策。

### 3.2 用户权威、证据可靠性和推断是否能排成一条等级

Claude Code 初稿将 user、verified、reviewed、proposed 排成权威梯度。Codex 指出这混淆“谁能定要求”和“事实是否成立”：引文存在不证明模型正确抽取命令，也不证明论文支持某结论。

Claude Code 明确回应：

> “三轴分离：同意，我收回统一等级。”

**最终选择：** 授权、证据生产者与语义判断分别记录。引文匹配只验证出处。明确用户要求绑定原文区间、digest 和作用域；条件/例子/转述保持候选。低负担自动记忆不能建立在错误的语义保证上。

### 3.3 研究什么时候停止，什么时候完成

Claude Code 初稿将预算到达、问题标为证据不足等作为停止条件。Codex 要求区分停止执行与履行调查义务，避免把“没查到”当完成，也避免强迫所有命题为 supported。

Claude Code 同意，并要求开始时展示调查义务，由评审核对义务是否匹配原问题。

**最终选择：** 完成由约定调查范围、方法、证据、反证与限制决定；负面/混合/未知答案可以是合格成果。预算耗尽仅终止当前推进，不自动通过验收。研究发布也可能涉及隐私或高影响决定，按真实风险授权。

### 3.4 原生 CLI 自由度与权限交集

双方同意扩大原生工具与连续 session 的价值。Codex 反对将本机委托整体视为不可信，也反对用工具名交集宣称任意 shell 已受相同限制。

Claude Code 同意按资源维度判断可强制边界，并补充原生工具事件需要独立来源类型 `runner_reported`。

**最终选择：** 授权集合和准入能力分开。硬要求无已验证强制实现时，回退受控或阻止对应动作；本机委托不能承诺不可绕过的私密/独立输入隔离。具体观察按 host/runner/provider/model/human 来源及完整度使用，不全盘丢弃原生执行成果。

### 3.5 原生能力是否应放到最后阶段

Codex 主张用户接受自由度，M2 就应交付一个真实 adapter×OS 的完整执行路径，而不是等全部记忆和研究系统完成。研究还需要无仓库 scratch，不应强迫选择工程开发。

Claude Code 条件同意：不永久排除某 OS，按能力实测；本机委托不能成为能力不足时的自动回退。

**最终选择：** M2 提供首个原生闭环、session 合同、scratch 和显式本机委托入口；其他组合受控回退。用户无需先建 Git 工程才能分析 CSV、做实验和生成图表。

### 3.6 预算与隐藏调用

Codex 指出未知 token 的下界不能提供硬上限；子任务、新 revision、重试都可能绕过每任务额度。

Claude Code 同意，指出原生调用内部可能无法限制每次模型请求。

**最终选择：** 稳定根任务 budget account，子任务/自动后续工作共享；宿主 invocation、时长、磁盘、并发可硬控，token/费用按报告能力标为实测、估计或未知，不伪造保证。

### 3.7 极简与开箱即用

Claude Code 指出默认断网的新工位会缺依赖，若首次任务逐项申请写入、shell、网络，所谓开箱即用就不成立。

**最终选择：** 首次一个项目执行授权卡，显示真正需要的能力；依赖准备先用受控只读缓存或私有副本，缺失时按锁文件在授权包源下载。任务不能任意写共享缓存。默认项目与成员关系自动生成，只有实质范围变化才再次询问。

## 4. 明确保留的裁决

以下内容曾有实质分歧，由 Codex提出裁决，再交 Claude Code 在第三轮回应。

| 争议 | 最终裁决与理由 |
| --- | --- |
| 独立 clone 用硬链接共享对象以节省空间 | 第一版不共享可写/硬链接 Git 对象，原生 shell 可以原地修改；接受磁盘成本。受控可用 linked worktree，真正验证 shared metadata 只读后再扩大使用 |
| 必需检查全生命周期只增不减 | 同一冻结政策不得被候选删改；新需求/政策版本允许有依据地替代旧检查，避免旧需求永远锁死项目 |
| 只有包含纠偏的 Attempt 成功，纠偏才算应用 | 目标修订首先持久化；输入准备/提交/确认与执行履行分开。尝试失败不能让新目标丢失；相同消息可重送，逻辑修订只应用一次 |
| 部署每次必须由用户点击 | 有明确环境/动作授权时可以自动推进；没有授权才问。授权和证据分开，不用重复点击替代真实部署核验 |
| Goal 只能 Thread 内串行 | Task 是项目持久对象；独立子任务并行，资源/预算受控，UI 默认折叠 |

## 5. 并行审阅补充的问题

三项独立静态审阅还补出以下实施缺口，均已纳入主稿：

- **同目标版本的证据失效：** 增加当前验收投影与 evaluation generation，避免旧运行重新标绿。
- **动态 handoff：** 冻结执行契约不禁止已有有界 PlanDelta，已接受内置计划仍保持不变。
- **写租约：** TTL 失效不能直接接管仍活着的 writer；核实停止或隔离原目录。
- **非 Git 部分应用：** 保存逐操作 journal，partial/uncertain 与完全无效果失败分开；不能宣称 hash 检查消除了外部编辑竞态。
- **资料撤销：** 追踪 session exposure/visibility epoch，退役已读撤销资料的 session，并清理派生内容。
- **原生指令加载：** AGENTS、CLAUDE.md、hooks/配置与 ContextPlan 使用同一已接受版本，不能一边自动加载旁路规则，一边声称完全受控。
- **单成员体验：** 低风险任务不默认强制独立 review；要求独立审查时沿用不同成员 ID，可用同一 CLI 的不同上下文但不冒充跨模型。
- **M1 的完整性：** 最低项目 scope、确切引用读取和 deterministic brief 必须在 M1 实现，不能把新会话接续留到 M3。
- **混合项目：** 研究→实验→工程实施使用同一 Task/依赖/验收内核，而非两种互不相通的项目模式。

## 6. 第三轮：最终裁决与剩余边界

Claude Code 在第三轮阅读的是本轮修订的决策摘要，没有再次完整读取修订后主稿。它给出的结论是：

> “可交付为 RFC（可实施设计草案），不是实机验证，也不是生产就绪。没有需要改架构、也没有需要再开一轮评审的阻断矛盾。”

它明确撤回硬链接共享对象和全生命周期检查只增不减的建议，同意纠偏先持久化目标、状态与输入回执分开；对已有授权自动部署/合并的条件是预授权必须绑定目标分支/环境、风险范围与证据前提。

最后提出的两项措辞冲突已在主稿修正：

1. **并行任务需要独立内部 Thread。** 仍保留同 Thread 单活跃 Run；根对话只呈现折叠进度，不能让并行消息破坏现有轮次语义。
2. **本机委托不扩大清理承诺。** session 与连接配置分开，宿主管理历史才可承诺清理；不能混入用户终端历史再声称永久清除。

第三轮还提出四个实施前必须明确的细节，已写入主稿及阶段约束：

- M2 冻结检查定义的文件/脚本/runner/helper 摘要与观察粒度，不只冻结 `npm test` 字符串。
- M2 用 Agent 不可写的宿主 Git 元数据作为可信来源，候选对象导入需完整性校验，禁用项只是纵深防御。
- M2 已检出分支的自动集成仅在干净、预期 HEAD 和独占条件下使用 ff-only；否则保留可集成成果。
- M4 acknowledged 取自 runner 接收事件，不能取模型复述；续接显式带替代记录，要求是否履行由新版验收判断。

Codex 保留一项具体实现取舍：测试 ID 缺失或新增 skip 必须进入差异审查，但正常测试重构不逐条向用户索要批准；只有降低必需业务验收才要求用户修订依据。机器检查版本与执行事实，语义等价由具备来源的审查判断。

## 7. 最终检查范围

主稿覆盖产品/视觉、领域对象、上下文/记忆、权限与原生执行、编排、工程/研究、验收、存储/API/Go 模块、迁移和测试策略。所有新能力都标为设计；原始产品文档和上下文提案没有被改成已实现行为。

文档检查包含本地链接、代码围栏、空白和仓库差异；不运行产品测试来给尚未实现的架构背书。CLI 沙箱、供应商表现、长期任务质量和跨平台能力仍需按主稿 M0–M5 完成真实验证。

## 8. 用户后续确认：协作预算可配置（2026-11-04）

用户确认在设置中提供可自由调整的协作预算，默认沿用自动续办 20 次、并行 4 个分支/2 个写分支、同问题修复 3 轮、连续无进展失败 2 次。本次仅更新设计，没有再次调用 Claude Code，也未实现设置界面。

主稿第 9.4 节据此补全设置入口、全局默认/项目覆盖/根任务快照、运行中修改、累计计数及耗尽行为。并发槽满正常排队，不要求扩额；累计额度和失败循环达到上限才暂停对应推进。已有任务预算需要明确调整，修改默认值不清空用量或自动复活暂停/取消的任务。权限模式与预算独立，完全访问也不自动取消协作预算。

## 9. 用户确认七项补充并授权交接实现（2026-11-04）

用户确认以下新增/细化方向，要求统一写入主稿并检查后交给其他 Agent 实现；本轮没有再调用 Claude Code。第 1–6 节为先前实际讨论，历史名称与当时取舍保留；最终规则以主稿和本节的后续确认优先。

| 决策 | 更新结果 |
| --- | --- |
| D1 持久任务之间直接 A2A | 增加消息信封/逐目标回执、原文追问/答疑唤醒、委派和责任转移、背压及失败回传 |
| D2 coder 主动请求 reviewer | 已授权成员自动选人/复核；工具持久回执生成 UI @ 卡，普通助手文本不派发 |
| D3 披露与注入分开 | 平台执行用户范围，协调者只选相关材料；有权但未注入的资料可按需读取 |
| D4 摘要不代替证据 | 明确摘要生成者、条件/反证/缺口与来源版本；接手者查原文、质疑并请原负责人解释 |
| D5 持续范围授权 | 项目/任务意图形成可复用 Grant，范围内协作与执行不逐步审批，只有真实新增范围才处理 |
| D6 三权限模式 | 受控、项目内自主、完全访问；首次受控，完全访问一次选择持续生效。旧“本机委托”改称“完全访问”，不是第四档 |
| D7 可配置协作预算 | 默认 20/4/2/3/2，设置/项目覆盖/根任务快照/运行中调整，权限切换不重置额度 |

文档检查还修正了实现所需的状态边界：长等待使用 yielded 段终态；持久等待 predicate 防止丢失唤醒；根取消控制 owned 子树；扩权需新 Run；预算分已用/预留并统计实际分支；未决副作用不能提前完成任务；多分支问题的回答绑定稳定 question ID。

入口统一指向主稿：原上下文提案标历史，product 标当前行为，AGENTS 增加重构目标入口。主稿第 15.1 节将 D1–D7 对应到 M1–M4 阶段与可观察验收；第 17 节单列 adapter/OS/来源定位等必须实测的关闭条件。本文记录的是设计检查，不声称功能已经实现。

## 10. 更新后的交接检查（2026-11-04）

主代理与三个独立审阅视角检查了权限/披露、编排/预算和产品交接一致性，并对发现的问题进行了定向复核。最后修正包括：

- 所有派生记忆/产物继承披露范围，不能通过“接受为项目记忆”绕过私密限制。
- 任务转移停止旧负责人的全部执行，包括只读推理；新 owner 接受不需要先取得被旧 Run 占用的执行槽。
- 下调预算可以重分配未启动 Run 的预留，与取消 Run 分开；跨根任何新增模型工作都有明确付款/授权归属。
- 新标准成员能力上限与实际项目 Grant 分开，一次开发授权可落地；旧成员明确禁用不被模式切换暗中覆盖。

上述问题修复后，三个审阅视角均确认其指出的阻断已消除。主稿还检查了 D1–D7 到阶段/验收的映射、章节引用、本地链接、代码围栏、空白及文档入口关系。当前结论为：**文档层面未发现遗留的实施阻断矛盾，可按主稿分阶段交接实现。** 这不是对未来代码正确性、真实 CLI 隔离或长期项目完成率的保证；相关关闭条件仍由主稿第 17 节约束。

本轮仅修改设计与入口说明，没有实现应用功能、运行产品测试、提交代码或调用 Claude Code。
